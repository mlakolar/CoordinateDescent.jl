Coordinate descent, losses and options

CoordinateDescent.coordinateDescent! — Function
coordinateDescent!(x, f, g, options=CDOptions(); rng=Random.default_rng(), kwargs...)
solve!(x, f, g, options::CDOptions; rng=Random.default_rng(), kwargs...)

Minimize f(x) + g(x) by coordinate descent and store the solution in x. The loss f is one of CDLeastSquaresLoss, CDWeightedLSLoss, CDSqrtLassoLoss and CDQuadraticLoss, a loss of ProximalBase that ProximalSolvers's coordinate descent takes (LeastSquaresLoss, a least-squares GLMLoss, QuadraticFunction, KronQuadratic, possibly scaled as in (1/n) * LeastSquaresLoss(y, X)), a model of ProximalSolvers (ProximalSolvers.CDModel), or a user-defined CoordinateDifferentiableFunction. The penalty g separates across coordinates (NormL1, ZeroFunction, ElasticNet, MCP, SCAD, … from ProximalBase, or another penalty, see below) and x is a SparseIterate or a SymmetricSparseIterate, or g is a group lasso penalty GroupNormL2 and x an AtomIterate (see below).

The descent is the coordinate descent of ProximalSolvers (ProximalSolvers.CDSolver, called through ProximalSolvers.solve!) with the options of CDOptions. It alternates between full passes over all coordinates and passes over the nonzero coordinates only (the active set). It stops when a full pass is followed by a pass in which no coordinate changes by more than options.optTol, or after options.maxIter passes. In the second case x may be far from the minimizer, and a warning is issued.

If options.warmStart is true, the descent starts from the supplied x. Otherwise x is set to zero and, for NormL1 and GroupNormL2, the problem is solved along a geometric sequence of options.numSteps penalty levels that decreases from the smallest λ0 with zero solution to g.λ0, each one warm started from the previous solution. Coordinates with zero penalty weight are left out when finding that λ0. For a SparseIterate or an AtomIterate, each penalty level is screened with the sequential strong rule, as in LassoPath.

The keyword arguments kwargs are fields of CDOptions that replace those of options, as in coordinateDescent!(x, f, g; optTol=1e-8). With order = :random, the coordinates are visited in an order drawn from rng; pass a seeded generator, such as Xoshiro(1), for reproducible passes without reseeding the global one.

coordinateDescent! returns x. solve! (a method of ProximalSolvers.solve!) does the same and returns a ProximalSolvers.CDResults: the number of passes (including those on the path of penalties when warmStart is false), whether the stopping rule was met (converged), the largest scaled change of a coordinate in the last pass (maxchange) and the tolerance it was compared with, and the objective minimum. Passing a CDInfo as the fifth argument of coordinateDescent!, to be filled in with this information, is deprecated.

A dense Vector x is also accepted; it is converted to a SparseIterate, or to an AtomIterate for GroupNormL2, and overwritten with the solution.

Group lasso

For g = GroupNormL2(λ0, groups, w), g(x) = λ0 Σₖ wₖ ‖x[Gₖ]‖₂, the coordinates are the groups: x is an AtomIterate with the groups of g, such as AtomIterate(p, g.groups), and the active set is its set of active groups. Each step minimizes over one group G the quadratic with curvature L that majorizes f around x, plus the penalty: x[G] ← (1 - λ0 wₖ / (L ‖u‖₂))₊ u with u = x[G] - ∇_G f(x) / L (groupwise majorization descent; Yang and Zou, A fast unified algorithm for solving group-lasso penalized learning problems, 2015). For CDLeastSquaresLoss, with or without intercept, L is the largest eigenvalue of X[:, G]'X[:, G] / n (centered), and for CDQuadraticLoss that of A[G, G]; user-defined losses do not take groups. The stopping rule takes the largest change of an entry in the pass, as for single coordinates. The path starts from maxₖ ‖∇_Gₖ f(0)‖₂ / wₖ over the penalized groups, and the strong rule keeps the groups with ‖∇_G f‖₂ ≥ (2λ - λprev) wₖ. Groups with zero weight are not penalized, and the groups must cover all coordinates, so a coordinate that is not penalized needs a group of its own with zero weight.

Other penalties

A separable penalty g(x) = Σₖ gₖ(xₖ) of another type, a subtype of ProximalBase.AbstractFunction with ProximalBase.isseparable true for it, needs the proximal operator of one entry, ProximalBase.prox_entry(g, v, k, γ), which returns argmin_z gₖ(z) + (z - v)² / (2γ). The built-in losses take this proximal step on the quadratic in x[k], so they accept such a penalty, and so does a user-defined loss whose descendCoordinate! calls ProximalBase.prox_coordinate! (see CoordinateDifferentiableFunction). Such a penalty has no path of penalty levels: with warmStart = false, the descent starts from zero and solves at g directly.

Anderson acceleration

With anderson = K in CDOptions, which needs order = :cyclic, the passes over the active set are accelerated (Bertrand and Massias, Anderson acceleration of coordinate descent, 2021): every K + 1 passes over an unchanged active set, the iterates are extrapolated and the extrapolated point is kept if it lowers the objective. It needs a SparseIterate or a SymmetricSparseIterate, and a loss whose value the model knows (the built-in losses, or a callable user-defined loss). It pays off when coordinate descent needs many passes, as at small penalties and with correlated columns. It keeps the weakness of the cyclic order when the columns share a strong common factor, where order = :random is much faster.

Momentum

With momentum (momentum in CDOptions), each pass over the active set starts from the extrapolated point xₖ + βₖ (xₖ - xₖ₋₁), with Nesterov's βₖ = (k - 1) / (k + 2); the momentum restarts when the step of a pass points against it (O'Donoghue and Candès, 2015), after a full pass, and when the active set shrinks. The cache of a built-in loss moves with the point, at the cost of a few vector operations per pass; a user-defined loss is initialized at the extrapolated point. It needs a SparseIterate or a SymmetricSparseIterate. Unlike Anderson acceleration, it works with the random order, so it also helps when the columns share a common factor; with the cyclic order it can stall.

By default (momentum = nothing) it is used with order = :random, a SparseIterate and a built-in loss other than KronQuadratic, and not otherwise. momentum = true asks for it with a user-defined loss as well, which can pay off when initializing the loss costs less than a pass; momentum = false turns it off.

CoordinateDescent.CoordinateDifferentiableFunction — Type
CoordinateDifferentiableFunction

Supertype of user-defined smooth losses f that coordinateDescent! can minimize. A subtype caches whatever it needs (for example residuals) to make coordinate updates cheap, and implements

  • initialize!(f, x): set the cache for the iterate x
  • gradient(f, x, k): coordinate k of the gradient of f at x
  • numCoordinates(f): number of coordinates
  • descendCoordinate!(f, g, x, k): update coordinate k of x and the cache

and optionally coordinateScale(f, k) and responseScale(f), which make the stopping rule independent of the units of the data (see CDOptions), fullGradient!(grad, f, x), a faster way to compute the whole gradient, and f(x), the value of f at x from the cache, which Anderson acceleration needs (anderson in CDOptions). These functions are not exported; extend them as CoordinateDescent.initialize! and so on. The four required functions have no methods of their own, so a missing method raises a MethodError that lists the methods that exist.

The penalty g enters only through descendCoordinate!. A loss whose step ends with the proximal operator of g on coordinate k, ProximalBase.prox_coordinate!(x, g, k, γ), works with every separable penalty of ProximalBase and with user-defined ones (see coordinateDescent!).

Coordinate descent runs on ProximalSolvers, which takes such a loss through a model (ProximalSolvers.CDModel); a loss written for ProximalSolvers directly, as a CDModel, is also accepted.

CoordinateDescent.CDLeastSquaresLoss — Method
CDLeastSquaresLoss(y, X; intercept=false)

The least squares loss f(β) = ‖y - Xβ‖² / (2n), as the model of ProximalSolvers for (1/n) * LeastSquaresLoss(y, X) (see ProximalSolvers.cdmodel). It caches the residuals r = y - Xβ, so a coordinate update costs O(n), and reads X and y in place.

With intercept, the loss is minimized over an unpenalized intercept as well, f(β) = min_β₀ ‖y - β₀ - Xβ‖² / (2n), whose minimizer is β₀ = ȳ - x̄'β for the column means x̄ and the mean ȳ of y (ProximalSolvers.intercept(f, β)). The columns and y are centered on the fly, so X is not copied, and the residuals are y - β₀ - Xβ (ProximalSolvers.residuals(f)).

A column that the loss does not depend on, a zero column or, with intercept, a constant one, gets the minimizer of the penalty nearest zero. y and X must not contain NaN or Inf.

On an AtomIterate, for the group lasso, a group G is updated at once, with the largest eigenvalue of the centered X[:, G]'X[:, G] / n as the curvature.

CoordinateDescent.CDQuadraticLoss — Method
CDQuadraticLoss(A, b)

The quadratic f(x) = x'Ax / 2 + b'x with symmetric A, as the model of ProximalSolvers for QuadraticFunction(A, b). It caches Ax, so a coordinate update costs O(p). With A = X'X/n and b = -X'y/n it gives the same minimizer as CDLeastSquaresLoss.

A coordinate with A[k, k] = 0, which f does not depend on when A is positive semidefinite, goes to the minimizer of the penalty nearest zero. A and b must not contain NaN or Inf. A dense Matrix A is used as it is, as in version 0.6; any other matrix is copied into one.

On an AtomIterate, for the group lasso, a group G is updated at once, with the largest eigenvalue of A[G, G] as the curvature.

CoordinateDescent.CDSqrtLassoLoss — Method
CDSqrtLassoLoss(y, X; intercept=false)

The square-root lasso loss f(β) = ‖y - Xβ‖, as the model of ProximalSolvers for ProximalSolvers.SqrtLeastSquaresLoss(y, X). It caches the residuals r = y - Xβ and the squared column norms. With intercept, f(β) = min_β₀ ‖y - β₀ - Xβ‖, minimized by β₀ = ȳ - x̄'β; as in CDLeastSquaresLoss, the columns and y are centered on the fly.

This loss is not smooth where r = 0, so coordinate descent minimizes f + g over a coordinate exactly instead of using a quadratic approximation. It takes the penalty NormL1 only.

CoordinateDescent.CDSqrtQuadraticLoss — Method
CDSqrtQuadraticLoss(A, b, c; check=true)

The square-root lasso loss from sufficient statistics, f(x) = √(x'Ax + 2b'x + c), with symmetric positive semidefinite A and a nonnegative quadratic, as the model of ProximalSolvers for ProximalSolvers.SqrtQuadraticFunction(A, b, c; check). With A = X'X/n, b = -X'y/n and c = y'y/n it is ‖y - Xx‖ / √n, the loss of CDSqrtLassoLoss divided by √n, without the data: it caches Ax and the value of the quadratic, so a coordinate update costs O(p) instead of O(n), and checking a coordinate that does not move costs O(1). It pays off when n > p, and when many fits share A. It also solves the scaled lasso of one variable on the others from their covariance matrix S: A = S, b = -S[:, j] and c = S[j, j], with an infinite penalty weight on coordinate j, which keeps it at zero (see scaledLasso!).

As for CDSqrtLassoLoss, coordinate descent minimizes f + g over a coordinate exactly, for NormL1 only. A, b and c must not contain NaN or Inf, and A must be symmetric; checking A costs O(p²), as much as a few passes, so check = false skips it when many losses share a checked A, as the columns of a covariance matrix do. A dense Matrix A is used as it is.

CoordinateDescent.CDWeightedLSLoss — Method
CDWeightedLSLoss(y, X, w)

The weighted least squares loss f(β) = ∑ᵢ wᵢ (yᵢ - Xᵢ'β)² / (2n), as the model of ProximalSolvers for (1/n) * GLMLoss(ProximalBase.Squared(), y, X; weights = w). It caches the residuals r = y - Xβ and the weighted squared column norms.

y, X and w are read in place, so changing them (as locpolyl1 does) changes the loss for the next solve. They are checked for NaN or Inf and the weights for negative entries only when the loss is built, so build it from initialized buffers. A coefficient whose column does not enter the loss (∑ᵢ wᵢ Xᵢₖ² = 0) goes to the minimizer of the penalty nearest zero.

CoordinateDescent.CDInfo — Type
CDInfo()

Convergence information that coordinateDescent! fills in when it is passed as the last argument. Deprecated: solve!(x, f, g, options) (see coordinateDescent!) returns the same information, and more, in a ProximalSolvers.CDResults: passes for iterations, converged, maxchange for maxChange, tolerance, and the objective minimum.

  • iterations: number of passes over the coordinates, including those on the path of penalties when warmStart is false
  • converged: whether the stopping rule was met before maxIter passes
  • maxChange: largest change of a coordinate in the last pass, scaled as described for optTol in CDOptions
  • tolerance: the threshold maxChange is compared with

CoordinateDescent.CDOptions — Type
CDOptions(; maxIter=100_000, optTol=1e-7, order=:random, warmStart=true,
            numSteps=50, relativeTol=true, anderson=0, momentum=nothing)
CDOptions(o::CDOptions; changes...)

Options for coordinateDescent! and the lasso solvers, which run the coordinate descent of ProximalSolvers (ProximalSolvers.CDSolver) with them. The second form copies o with the fields named in changes replaced, as in CDOptions(o; warmStart=false). The solvers also take these fields as keyword arguments, lasso(X, y, λ; maxIter=10_000, optTol=1e-8), which change the options passed to them.

  • maxIter: maximum number of passes over the coordinates; reaching it without convergence gives a warning
  • optTol: convergence tolerance on the largest change of a coordinate in a pass. With relativeTol, the change of coordinate k is measured as |Δxₖ| ⋅ coordinateScale(f, k) and compared with optTol ⋅ responseScale(f), so that the tolerance does not depend on the units of the data; for the least squares loss these scales are ‖X[:, k]‖ / √n and ‖y‖ / √n. Otherwise |Δxₖ| is compared with optTol
  • order: the order in which a pass visits the coordinates
    • :random: a new random order in every pass, drawn from the random number generator rng that the solvers take as a keyword argument, by default the global one (Random.default_rng())
    • :cyclic: the order 1, 2, …
    The cyclic order can be faster on some designs, but much slower when the columns are strongly correlated with each other. randomize = true and randomize = false are the same as order = :random and order = :cyclic
  • warmStart: start from the supplied iterate; otherwise start from zero and follow a path of decreasing penalties
  • numSteps: number of penalty levels on that path when warmStart is false
  • relativeTol: see optTol; losses that do not define the scales, such as user-defined ones, use the absolute rule either way
  • anderson: the memory K of Anderson acceleration, 0 for none (see coordinateDescent!); it needs order = :cyclic
  • momentum: Nesterov momentum on the passes over the active set (see coordinateDescent!). The default, nothing, uses it where it is known to help: with order = :random, a SparseIterate and a built-in loss. true asks for it with any loss, and needs order = :random; false turns it off

CoordinateDescent.IterLassoOptions — Type
IterLassoOptions(; maxIter=20, optTol=1e-2, initProcedure=:Screening,
                   sinit=5, σinit=1.0, optionsCD=CDOptions())
IterLassoOptions(o::IterLassoOptions; changes...)

Options for feasibleLasso!, which alternates a lasso fit with an update of the penalty loadings, and for scaledLasso!, which uses only optionsCD (since version 0.6.1 it solves the square-root lasso in one run of coordinate descent instead of alternating a lasso fit with an update of the noise level). The second form copies o with the fields named in changes replaced. The two solvers also take these fields as keyword arguments, as in feasibleLasso!(x, X, y, λ0; maxIter=50).

  • maxIter: maximum number of outer iterations
  • optTol: tolerance on the relative change of the noise level or loadings
  • initProcedure: how the procedure is initialized
    • :Screening: least squares on the sinit columns of X most correlated with y
    • :InitStd: noise level σinit
    • :WarmStart: the iterate passed in
  • sinit, σinit: used by :Screening and :InitStd
  • optionsCD: CDOptions for coordinate descent; in feasibleLasso! each lasso fit is warm started from the previous one, so its warmStart is not used there
